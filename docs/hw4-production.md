# ДЗ 4. Промышленная версия

MVP - один процесс, который при каждом запуске читает файлы и строит индекс
Для ежедневного использования этого почти достаточно, но не хватает автоматического обновления данных, контроля качества при изменениях и наблюдаемости

## Целевая архитектура

```
              +------------ пайплайн данных (по расписанию / вручную) ------------+
 LMS, Т-Обр., | парсер hse-lms refresh -> CSV/Markdown -> проверка схемы и свежести |
 письма, чаты |                                    +-> индекс (BM25, позже эмбеддинги)
              +--------------------------------------------------------------------+
                                                       | index.json + версия данных
                                                       v
 CLI, почта, календарь -> сервис ассистента: маршрутизатор -> инструменты -> LLM (опц.)
                                |                                         |
                                +-------- журнал запросов (JSONL) <-------+
                                                       v
                                          отчет мониторинга и алерты
```

## Компоненты

1. **Пайплайн данных** Выгрузки обновляет мой парсер (`hse-lms refresh`)
   Дальше нужно проверить, что в CSV есть нужные колонки и они не пустые, и пересобрать индекс
2. **Сервис** Тот же `Assistant`, к которому подключены CLI, почта, календарь и MCP
   Telegram-бот не подошел: мессенджер заблокирован
3. **Инструменты** Сейчас это поиск по материалам и список будущих дедлайнов
   Следующими могут быть оценки по курсу и расписание на день
4. **Генерация** Только локальная модель в Ollama, поэтому персональные данные не уходят наружу
   Модель получает только найденные фрагменты
   Если она недоступна, ответ будет без нее
5. **Проверка изменений** Перед каждым изменением запускаются тесты на фикстурах и `assistant eval`
   Изменение не принимается, если hit@3 ниже 0,8

## Интеграции

| Команда | Что делает |
| --- | --- |
| `digest` | письмо на Яндекс Почту с дедлайнами на неделю и алертами мониторинга |
| `sync-calendar` | сроки в Яндекс Календаре с напоминанием за сутки; отправляются только изменения |
| `schedule install` | дайджест каждый день в 09:00, календарь каждые 30 минут |
| `mcp` | MCP-сервер: поиск, дедлайны и мониторинг для любой LLM, только чтение |

Почта работает по SMTP, календарь по CalDAV, пароли приложений лежат в `.env`
У каждого события постоянный идентификатор, поэтому перенос срока обновляет событие, а не создает копию
Тесты проверяют почту, календарь и MCP на поддельных серверах без сети

## Пайплайн изменений

```
изменение кода -> unit-тесты -> eval на размеченном наборе -> сравнение с прошлым результатом -> релиз
новые данные   -> проверка схемы и свежести -> пересборка индекса -> eval (смоук) -> замена индекса
```

## Риски и решения

| Риск | Решение |
| --- | --- |
| Устаревшие данные, ассистент называет старые сроки | метрика возраста данных и алерт > 7 дней |
| Утечка персональных данных | данные вне репозитория, письмо только на свой адрес, журнал локальный |
| Через MCP данные попадают в чужую модель | инструменты только читают; в README предложен локальный клиент (LM Studio) |
| LLM придумывает ответ | только фрагменты в контексте, порог уверенности до вызова LLM, источник в ответе |
| Перефразы не находятся лексическим поиском | словарь основ и сокращений (сделано в ДЗ 5), дальше эмбеддинги |
| Изменение формата выгрузки ломает загрузку | проверка схемы CSV (пока не сделана), тесты на фикстурах |
